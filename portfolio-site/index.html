🍄 Super Mario Bros. (1985) Unity 2D 모작

패미컴 원작의 물리 법칙, 조작감, 스테이지 기믹을 Unity 2D로 재현한 개인 학습 프로젝트입니다. 이 페이지는 면접 전 스스로 복기할 수 있도록 전체 구조 · 구현 방법 · 사용된 디자인 패턴 · 예상 질문을 한 곳에 정리한 자료입니다.

Unity 2022.3.62f3 C# 2D Physics (Rigidbody2D) Singleton Pattern State Machine Interface 기반 다형성 Coroutine 연출 Scene 간 데이터 유지
01

프로젝트 개요

이 프로젝트는 NES 슈퍼마리오 브라더스 1-1 스테이지를 Unity 2D로 모작한 것입니다. 단순히 비주얼만 따라 만든 것이 아니라, 원작 특유의 "묵직하면서도 정교한" 조작감(가속도, 관성, 대시 점프, 가변 중력)을 수치 단위로 재현하는 데 초점을 맞췄습니다.

목적: Unity 2D 물리/애니메이션/씬 관리 구조에 대한 학습과, 실제 동작하는 결과물을 포트폴리오로 남기는 것. 그래픽·사운드 리소스의 저작권은 Nintendo에 있으며, 비상업적 학습용 팬 메이드 프로젝트입니다.

한눈에 보는 구현 범위

플레이어 (마리오)

SMB1 원작 수치 기반 가속/관성 이동, 대시 점프, 가변 점프 중력, Small→Super→Fire 3단 상태 변신, 무적/사망 연출, 워프/깃발 클리어 연출.

적 (Goomba / Koopa)

IEnemy 인터페이스로 통일된 피격 처리(밟기/블록타격/파이어볼), 화면 밖 슬립(sleep) 최적화, 쿠파의 3단 상태(걷기/껍질정지/껍질발사).

블록 & 아이템

물음표/벽돌/숨김/코인 벽돌 4종 블록, 버섯/꽃/별 아이템의 AI 이동, 블록 파괴 시 4파편 물리 연출.

매니저 계층

GameManager·SoundManager 싱글톤으로 씬 전환 간 점수/코인/목숨/시간/오디오 유지, PlayerPrefs 최고점수 저장.

연출 시퀀스

워프 파이프(암전 → 이동 → 카메라 재설정), 깃발 클리어(하강 → 점프 → 성으로 걷기 → 시간 점수 정산) 코루틴 연출.

디스플레이 대응

256×240 NES 원본 비율을 어떤 해상도에서도 유지하는 레터박스(Viewport Rect) 스크립트, 전체화면 토글.

02

폴더 & 스크립트 구조

스크립트는 역할별 폴더로 나뉘어 있습니다. 이 자체가 "기능(role)별 분리"라는 설계 의도를 보여줍니다.

Assets/2. Scripts/ ├── Mario/ │ ├── MarioCtrl.cs // 플레이어 이동·점프·상태·연출을 전부 소유하는 핵심 클래스 (God Object에 가까움, 한계점 참고) │ └── PlayerHeadCheck.cs // 머리 충돌(블록 아래서 치기) 전담, 단일 책임으로 분리됨 ├── Enemy/ │ ├── IEnemy.cs // 피격 인터페이스 (Squished/HitFromBelow/HitByFireball) │ ├── Goomba.cs // 직선 이동 + 3가지 사망 처리 │ └── Koopa.cs // 3단 상태 머신(Walking/ShellIdle/ShellMoving) ├── Items/ │ ├── MushroomAI.cs // 버섯: 좌우 이동 + 벽 반사 │ ├── StarAI.cs // 별: 좌우 이동 + 통통 튕김(bounce) │ ├── FlowerItem.cs // 꽃: 제자리 고정형 아이템 │ └── UnderCoin.cs // 맵에 고정 배치된 코인 ├── Blocks/ │ ├── InteractableBlock.cs // 물음표/벽돌/숨김/코인 블록 통합 처리 (BlockType enum) │ ├── BrickDebris.cs // 벽돌 파괴 파편 1개 단위 물리 처리 │ ├── WarpPipe.cs // 파이프 진입/탈출 연출 + 카메라 모드 전환 │ ├── FlagPole.cs // 깃대 높이별 점수 계산 + 클리어 트리거 │ └── DeathZone.cs // 구덩이(낙사 트리거) ├── Effects/ │ └── Fireball.cs // 파이어볼 발사·바운스·적 피격·자동 디스폰 ├── Manager/ │ ├── GameManager.cs // 싱글톤. 점수/코인/목숨/시간/씬전환 총괄 │ ├── SoundManager.cs // 싱글톤. BGM/SFX 재생 총괄 │ ├── HUDManager.cs // GameManager 데이터를 화면 텍스트로 반영(View 역할) │ ├── TitleMenuManager.cs // 타이틀 화면 메뉴 커서 & 최고점수 표시 │ ├── TransitionManager.cs // 인트로/타임업/게임오버 3종 전환 화면 제어 │ └── Destructor.cs // 범용 오브젝트/자식 파괴 유틸리티 └── UI/ ├── FollowCamera.cs // 카메라 추적(X축) + Y축 고정/정적 모드 전환 ├── CameraResolution.cs // 256x240 비율 강제(레터박스) └── FloatingScore.cs // 점수 팝업 텍스트(상승 후 자동 소멸)

씬(Scene) 흐름

총 3개 씬이 SceneManager.LoadScene()으로 순환하며, GameManager/SoundManager는 DontDestroyOnLoad로 이 흐름 전체에서 살아남습니다.

scTitle→ scTransition (LevelIntro)→ scMario1_1→ scTransition (TimeUp / GameOver)

예를 들어 목숨을 잃으면(GameManager.LoseLife()) 목숨이 남았는지에 따라 TransitionType.LevelIntro 또는 TransitionType.GameOver로 상태를 세팅한 뒤 scTransition 씬을 로드하고, 그 씬의 TransitionManager가 GameManager.Instance.currentTransition 값을 읽어 어떤 패널을 보여줄지 스스로 판단합니다. 즉 씬 전환의 "무엇을 보여줄지 결정하는 상태"는 항상 싱글톤이 들고 있고, 각 씬은 그 상태를 읽기만 하는 구조입니다.

03

사용한 디자인 패턴 / 설계 기법

1. 싱글톤 (Singleton)

GameManager, SoundManager가 public static X Instance + DontDestroyOnLoad 조합으로 구현됨. 씬이 계속 바뀌는 게임 특성상 점수·오디오처럼 "게임 전역에 하나만 있어야 하는 상태"를 유지하기 위해 선택.

✔ 왜: 씬 전환마다 매니저를 새로 만들면 점수/코인/BGM이 끊긴다. 이미 인스턴스가 있으면 새로 생성된 쪽을 파괴하는 가드 코드로 중복 생성을 방지.

2. 인터페이스 기반 다형성 (Interface Polymorphism)

IEnemy 인터페이스(Squished / HitFromBelow / HitByFireball)를 두어 MarioCtrl, InteractableBlock, Fireball이 상대가 굼바인지 쿠파인지 몰라도 GetComponent<IEnemy>()로 동일하게 호출 가능.

✔ 왜: 적 종류가 늘어나도(예: 뻐끔플라워 추가) 호출부 코드는 전혀 안 바꾸고 새 클래스만 인터페이스를 구현하면 됨 — 개방-폐쇄 원칙(OCP).

3. 상태 머신 (State Machine)

MarioCtrl.currentState ("Small/Super/Fire") 와 Koopa.KoopaState enum (Walking/ShellIdle/ShellMoving)으로 상태별 분기. 상태 전이 시 콜라이더 크기, 애니메이터, 이동 로직이 함께 바뀜.

✔ 왜: "지금 어떤 모습이고 무엇을 할 수 있는가"가 게임 전반에서 반복적으로 필요한 조건이라, 상태값 하나로 여러 분기를 관리하는 편이 if 지옥보다 명확함.

4. 컴포넌트 기반 설계 (Component-based / 단일 책임)

머리 충돌만 담당하는 PlayerHeadCheck.cs를 별도 자식 오브젝트+컴포넌트로 분리. 발밑 groundCheck, 머리 headCheck도 별도 Transform으로 관리.

✔ 왜: 몸통 충돌(적과의 옆 충돌)과 머리 충돌(블록 타격)의 판정 로직이 섞이면 서로 다른 반응(데미지 vs 블록히트)이 꼬이기 쉬움. 물리적으로도 콜라이더를 분리하는 것이 Unity 방식에 부합.

5. 코루틴 기반 연출 시퀀싱 (Coroutine Sequencing)

변신 연출(TransformationSequence), 워프(WarpSequence), 깃발 클리어(ClearRoutine), 시간→점수 정산(CalculateTimeScoreRoutine) 모두 IEnumerator 코루틴으로 "시간에 따라 순서대로 일어나는 연출"을 표현.

✔ 왜: 여러 프레임에 걸친 연출(대기 → 이동 → 대기 → 애니메이션)을 상태 플래그와 Update 분기로 짜면 가독성이 크게 떨어짐. 코루틴은 순차적 흐름을 그대로 코드 순서로 표현 가능.

6. 데이터 기반 설정 (Inspector-Driven Configuration)

InteractableBlock.type(enum), WarpPipe.pipeType/exitDirection/setCameraStatic 등 거의 모든 기믹이 코드 수정 없이 인스펙터 값 조합만으로 다른 동작을 하도록 설계됨.

✔ 왜: 레벨 하나에 파이프/깃발/블록이 수십 개씩 배치되는데, 매번 스크립트를 새로 만들 수 없으므로 하나의 범용 스크립트 + 파라미터 조합으로 다양한 배치를 지원.

7. 지연 활성화(Lazy Wake) 최적화

Goomba/Koopa가 카메라와의 거리가 wakeUpDistance 이내로 들어오기 전까지 rb.simulated = false로 물리 연산 자체를 꺼둠. 화면 밖으로 멀어지면 오브젝트를 Destroy.

✔ 왜: 스테이지에 존재하는 모든 적이 항상 물리 연산을 하면 낭비가 크고, 원작에서도 화면에 들어오기 전엔 적이 움직이지 않는 특유의 느낌을 재현하려는 목적도 있음.

8. Getter 기반 상수 테이블 (Physics Constant Table)

MarioCtrl 내부에 MIN_WALK, ACC_RUN, JUMP_SPEED_RUN 등을 private float X { get { return 픽셀값 / PPU; } } } 형태의 읽기 전용 프로퍼티로 선언.

✔ 왜: 원작 SMB1의 물리 상수는 "픽셀/프레임" 단위 자료로 공개되어 있는데, 이를 Unity 단위(Unit)로 변환하는 공식을 상수마다 반복하지 않고 PPU(Pixel Per Unit) 하나만 바꾸면 전체가 같이 스케일되도록 설계.
04

마리오 물리 엔진 — 원작 조작감 재현

가장 공들인 부분입니다. Unity의 기본 Rigidbody2D + AddForce 조합이 아니라, 매 프레임 속도(velocity)를 직접 계산해서 대입하는 방식으로 SMB1 원작의 딱딱 끊어지는 느낌의 가속/감속을 재현했습니다.

1) 속도 기반 이동 — 가속·감속·스퀴드(Skid)

MarioCtrl.cs — FixedUpdate()

매 FixedUpdate마다 입력 방향(h)과 현재 속도(vel.x)의 부호를 비교해 3가지 경우로 분기합니다.

  • 입력 없음(h==0): Mathf.MoveTowards로 서서히 0을 향해 감속(마찰력, DEC_REL).
  • 같은 방향으로 가속: 달리기 버튼(Fire1) 유무에 따라 ACC_WALK/ACC_RUN을 더하고, 각각의 최고 속도(MAX_WALK/MAX_RUN)로 클램프.
  • 반대 방향 입력(스퀴드): 걷다가 반대로 꺾으면 원작처럼 미끄러지는 애니메이션(isSkidding)과 함께 더 큰 감속력(DEC_SKID)으로 빠르게 방향을 반전.
if (h == 0)
{
    // 입력이 없을 때: 서서히 멈춤 (마찰력)
    vel.x = Mathf.MoveTowards(vel.x, 0, DEC_REL * Time.fixedDeltaTime);
}
else
{
    if (Mathf.Sign(h) == Mathf.Sign(vel.x) || absVx < MIN_WALK)
    {
        // 같은 방향 가속
        float acc = isRunButtonHeld ? ACC_RUN : ACC_WALK;
        vel.x += h * acc * Time.fixedDeltaTime;
        vel.x = Mathf.Clamp(vel.x, -currentMaxSpeed, currentMaxSpeed);
    }
    else
    {
        // 반대 방향 입력 → 스퀴드(미끄러짐)
        isSkidding = true;
        vel.x += h * DEC_SKID * Time.fixedDeltaTime;
    }
}

2) 대시 점프 — 속도에 따라 달라지는 점프력/중력

점프 버튼을 누르는 "순간"의 |vel.x|를 기준으로 3단계(정지/걷기/달리기)를 판단하여 점프 속도(JUMP_SPEED_IDLE/JUMP_SPEED_RUN)와 그 이후 적용될 중력값(currentGravityBase)을 미리 결정해 둡니다. 이것이 원작 특유의 "빨리 달리다 점프하면 더 멀리, 더 오래 뜨는" 대시 점프의 핵심입니다.

3) 가변 점프(Variable Jump Height) — "누르는 시간"이 점프 높이를 결정

점프 키를 누르고 있는 동안(isJumpButtonHeld) 상승 중(vel.y > 0)이면 약한 중력(currentGravityHold)을, 키를 떼거나 하강 중이면 강한 중력(currentGravityBase)을 적용합니다. 마리오 게임 특유의 "톡 누르면 낮게, 꾹 누르면 높이" 점프하는 느낌은 점프력 자체가 아니라 중력을 프레임마다 스위칭해서 만듭니다.

왜 이 방식을 썼는가: Unity의 Rigidbody2D.gravityScale을 한 번만 설정하면 모든 상황에 같은 중력이 적용되어 점프 높이가 항상 동일해집니다. 매 프레임 상황(상승/하강, 키 입력 여부, 점프 시작 속도)에 따라 중력 자체를 다르게 계산해 vel.y에서 직접 빼주는 방식을 택해야 원작과 같은 "손맛"이 재현됩니다.

4) 숙이기(Crouch) — 콜라이더 실시간 리사이즈

슈퍼/파이어 상태에서 아래 키 입력 시 SetColliderSize/SetCheckers로 BoxCollider2D의 크기·오프셋과 groundCheck/headCheck의 위치를 작은 마리오 사이즈로 실시간 변경합니다. 복귀 시 원래 크기로 되돌립니다.

5) 밟기(Stomp) 판정

Goomba/Koopa의 OnCollisionEnter2D에서 playerRb.velocity.y < 0 && 플레이어 y좌표가 적보다 0.2~0.3f 이상 위에 있는지를 함께 검사해 "위에서 떨어져 밟은 것"과 "옆에서 부딪힌 것"을 구분합니다. 밟았을 때는 MarioCtrl.StompBounce()로 살짝 튕겨오릅니다.

05

마리오 상태 변신 시스템

Small⇄ Super⇄ Fire

변신 처리 흐름 (TransformationSequence)

TakeItem(string itemType)이 아이템 충돌 이벤트를 받아 현재 상태에 따라 코루틴 TransformationSequence(oldState, newState, oldSprite, newSprite, startInvincible)을 실행합니다.

  1. Time.timeScale = 0f로 게임을 잠시 멈추고 애니메이터를 끔 (연출 중 다른 입력/물리가 끼어들지 않도록).
  2. 큰 모습 ↔ 작은 모습 스프라이트를 3회 교차 출력해 원작의 "깜빡이며 커지는" 변신 연출 재현.
  3. 연출이 끝나면 ChangeMarioState(newState)로 실제 콜라이더 크기·애니메이터 컨트롤러를 교체하고 Time.timeScale = 1f로 복귀.
  4. 피격으로 인한 강등(Fire→Super, Super→Small)일 경우 startInvincible = true를 넘겨 변신 직후 무적 깜빡임 코루틴을 이어서 실행.

파이어 마리오 — 상/하체 분리 애니메이터

파이어 마리오는 상체(팔/파이어볼 투척)와 하체(다리/걷기)의 애니메이션을 독립적으로 재생해야 원작처럼 "뛰면서 위쪽으로 파이어볼을 던지는" 동작이 자연스럽습니다. 이를 위해 fireMarioBody라는 별도 부모 오브젝트 아래 upperAnim/lowerAnim 두 개의 Animator를 두고, 기본 몸통(mainSr)은 꺼둔 채 이 둘에게 이동/점프/숙이기 파라미터를 동시에 전달합니다 (UpdateAnimations()). 파이어볼을 쏠 때는 upperAnim.SetBool("isShooting", true)만 호출해 하체는 계속 달리는 채로 상체만 손을 뻗는 포즈가 됩니다.

별(Star) 무적 — 텍스처 스와핑 방식의 색상 반짝임

일반적으로 무적 반짝임은 색상 틴트(Color tint)를 주지만, 이 프로젝트는 스프라이트 텍스처 자체를 통째로 교체하는 방식을 사용합니다. MaterialPropertyBlock으로 _MainTex를 매 0.05초마다 레드/블랙/그린 팔레트로 순환 교체하고, LateUpdate()에서 매 프레임 다시 덮어써서 애니메이터가 그림을 바꿔도 항상 별 색이 유지되도록 강제합니다. 

private void LateUpdate()
{
    if (isStarInvincible)
    {
        // 애니메이터가 렌더링을 끝낸 직후, 무조건 텍스처를 덮어씀 (철벽 방어)
        ApplyStarTexture(currentStarTexture, currentUpperStarTexture, currentLowerStarTexture);
    }
}
왜 Update가 아니라 LateUpdate인가: Animator는 Update 이후 자체 타이밍에 스프라이트를 갱신합니다. Update에서 텍스처를 바꾸면 그 다음 애니메이터가 다시 원래 텍스처로 덮어써버려 반짝임이 보이지 않게 됩니다. LateUpdate에서 처리해야 "애니메이터가 그린 뒤 마지막에" 확실히 색이 남습니다.

별 상태에서는 Physics2D.IgnoreLayerCollision(Player, Enemy, true)로 플레이어-적 레이어 충돌 자체를 끄고, 대신 CheckStarEnemyCollision()에서 OverlapBoxAll로 몸통 범위의 적을 직접 탐지해 enemy.HitByFireball()을 호출하는 방식으로 처치합니다 (충돌 이벤트가 아닌 능동적 판정).

SuperSmall로 강등 + 무적 코루틴 시작

적 AI — Goomba & Koopa

공통 인터페이스: IEnemy

public interface IEnemy
{
    void Squished();        // 밟혔을 때
    void HitFromBelow();    // 블록 밑에서 맞았을 때
    void HitByFireball();   // 파이어볼/스타/등껍질에 맞았을 때
}

MarioCtrl, InteractableBlock, Fireball, 그리고 다른 Koopa 껍질까지 모두 상대의 실제 타입을 몰라도 GetComponent<IEnemy>()로 꺼내 동일한 3개 메서드만 호출하면 됩니다. 예를 들어 날아가는 등껍질이 굼바에 부딪히면 otherEnemy.HitByFireball()을 그대로 호출해 굼바를 처치합니다 — 등껍질 입장에서는 상대가 무엇인지 알 필요가 없습니다.

Goomba — 단순 직선 이동 + 3종 사망

  • Squished() (밟힘): 물리·콜라이더를 끄고 찌그러지는 애니메이션 후 0.5초 뒤 삭제, 100점.
  • HitFromBelow() (블록 아래에서 맞음): sr.flipY = true로 뒤집고 위로 튕겼다가 낙하, 2초 뒤 삭제.
  • HitByFireball(): HitFromBelow와 동일한 연출(뒤집혀서 날아감).

Koopa — 3단 상태 머신

Walking밟기→ ShellIdle옆에서 치기→ ShellMoving
상태이동밟혔을 때(Squished)
Walking일정 속도로 좌우 순찰, 벽 닿으면 반전ShellIdle로 전이 (걷기→껍질)
ShellIdle마찰력으로 서서히 정지플레이어 반대 방향으로 발사 → ShellMoving
ShellMoving고속 직선 이동, 부딪힌 적을 즉시 처치제자리에 멈춤 → ShellIdle

상태 전이는 ChangeState() 한 곳에서 콜라이더 크기·애니메이터 파라미터를 함께 갱신하도록 모아두어, "상태를 바꾸는 코드"와 "그 상태에 맞는 모습을 만드는 코드"가 흩어지지 않게 했습니다.

충돌 처리 우선순위가 중요한 지점: Koopa.OnCollisionEnter2D는 (1) 다른 적과의 충돌 → (2) 순수 벽 충돌 → (3) 플레이어와의 충돌 순서로 분기합니다. 특히 ShellMoving 상태에서 다른 적을 맞히면 return으로 벽 충돌 판정을 건너뛰어, "적을 뚫고 그대로 직진"하는 원작의 등껍질 특유의 느낌을 만듭니다.

최적화 — 화면 밖 슬립(Sleep) 처리

모든 적은 생성 시 rb.simulated = false로 시작합니다. 매 프레임 카메라와의 X거리(wakeUpDistance, 기본 12)를 검사하다가 거리 안에 들어오면 그제서야 물리 시뮬레이션을 켭니다. 반대로 카메라 뒤로 일정 거리 이상 멀어지면 Destroy(gameObject)로 제거해 불필요한 연산과 메모리를 아낍니다.

InteractableBlock — enum 기반 4종 블록 통합

public enum BlockType { Question, Brick, Hidden, CoinBrick }
타입동작

Hidden평소엔 SpriteRenderer가 꺼져 있다가(투명 블록) 처음 맞았을 때 모습을 드러내며 Question과 동일 로직 수행

벽돌 파괴 연출 — 4파편 물리

BreakBlock()은 좌상/우상/좌하/우하 4개의 BrickDebris 오브젝트를 생성하며, 미리 정의한 서로 다른 초기 속도(Vector2[])와 회전력(torques)을 각각 주입해 원작처럼 사방으로 흩날리는 파편을 연출합니다. 각 파편은 2초 뒤 자동 소멸.

블록 위 아이템/적 감지 — OverlapBoxAll

블록을 아래서 칠 때 CheckEnemyOnTop()이 블록 바로 위 좌표에 Physics2D.OverlapBoxAll로 박스를 그려 그 위에 있는 모든 콜라이더를 검사합니다. Enemy 태그면 HitFromBelow()를, 버섯/별 AI 컴포넌트가 있으면 BounceAndChangeDirection()을 호출해 "블록을 치면 그 위의 굼바가 죽거나 버섯이 튕겨서 반대로 걷기 시작하는" 원작 기믹을 재현합니다.

아이템 등장 연출

AppearItem() 코루틴이 아이템의 콜라이더/물리를 잠시 꺼둔 채 Vector3.MoveTowards로 블록 위 0.6f 만큼 서서히 밀어올린 뒤, 물리를 켜고 MushroomAI.StartMoving()/StarAI.StartMoving()을 호출해 비로소 좌우 이동을 시작시킵니다.

매니저 계층 & 싱글톤 설계

GameManager — 게임 전역 데이터의 단일 진실 공급원(SSOT)

점수, 코인, 목숨, 월드/스테이지, 남은 시간을 전부 소유하며, HUDManager는 이 값을 매 프레임 읽어 텍스트로만 반영합니다(즉 HUDManager는 로직이 없는 순수 View). 씬 전환이 필요한 모든 이벤트 (목숨 소진, 시간 초과, 스테이지 클리어)는 전부 GameManager를 거칩니다. 

public enum TransitionType { LevelIntro, TimeUp, GameOver }

public void LoadTransition(TransitionType type)
{
    currentTransition = type;       // 다음 씬이 읽을 상태를 미리 세팅
    isGameActive = false;      // 타이머 정지
    SceneManager.LoadScene(transitionSceneName);
}

이렇게 "상태를 세팅하고 씬을 로드"하는 패턴 덕분에 TransitionManager는 파라미터를 직접 주고받을 필요 없이 GameManager.Instance.currentTransition 하나만 읽어서 인트로/타임업/게임오버 3개 패널 중 무엇을 켤지 스스로 결정합니다.

100초 경고 연출 (TimeWarningRoutine)

남은 시간이 100초 이하가 되는 순간 코루틴이 기존 BGM을 끊고 경고음을 재생, 그 오디오 클립의 실제 길이(clip.length)만큼 정확히 대기한 뒤 빠른 템포의 BGM으로 전환합니다. 하드코딩된 대기 시간이 아니라 오디오 클립 자체의 길이를 참조하는 점이 핵심입니다.

SoundManager — BGM/SFX 분리 오디오소스

bgmSource(루프 음악)와 sfxSource(PlayOneShot 효과음)를 분리해 관리합니다. PlayOneShot을 쓰는 이유는 효과음끼리 서로 재생을 끊지 않고 겹쳐 재생되어야 하기 때문(예: 코인 연타 획득 시 사운드가 겹쳐 들려야 자연스러움)입니다.

PlayerPrefs를 이용한 최고 점수 영구 저장

int currentHighScore = PlayerPrefs.GetInt("HighScore", 0);
if (totalScore > currentHighScore)
{
    PlayerPrefs.SetInt("HighScore", totalScore);
    PlayerPrefs.Save();
}

클리어 시 시간 정산이 끝난 뒤 최고 점수를 비교/갱신하고, 타이틀 화면의 TitleMenuManager가 이 값을 다시 읽어 표시합니다.

카메라 & 레트로 해상도 대응

FollowCamera — 원작처럼 "뒤로는 안 밀리는" 카메라

targetX = Mathf.Max(transform.position.x, targetX)로 카메라의 새 목표 X좌표가 현재 위치보다 뒤로 가는 경우를 원천 차단합니다. 즉 마리오가 왼쪽으로 되돌아가도 카메라는 이미 지나온 오른쪽 경계를 넘어 왼쪽으로 돌아가지 않는, SMB1 원작의 "돌아갈 수 없는 카메라" 특성을 그대로 재현합니다. 지하 구간에서는 isStatic으로 카메라를 완전 고정하거나 lockY로 Y축만 고정하는 모드를 ConfigureCamera()로 전환할 수 있습니다.

CameraResolution — 256×240 레터박스

NES 원본 해상도(256×240) 비율과 현재 화면 비율을 비교해, 세로로 길면 위아래 블랙바, 가로로 길면 좌우 블랙바가 생기도록 Camera.rect(Viewport Rect)를 계산합니다. 실제 해상도를 강제로 바꾸는 대신 카메라의 뷰포트만 조절하는 방식이라 어떤 창 크기·모니터 비율에서도 원작 화면비가 절대 깨지지 않습니다. 

float targetRatio = 256f / 240f;
float currentRatio = (float)Screen.width / Screen.height;
float scaleHeight = currentRatio / targetRatio;

if (scaleHeight < 1f) { /* 위아래 블랙바 */ }
else            { /* 좌우 블랙바 */ }

연출 시퀀스 — 워프 파이프 & 깃발 클리어

WarpPipe — 방향/카메라를 인스펙터로 조합하는 범용 파이프

PipeType(VerticalIn/HorizontalOut), exitDirection, setCameraStatic/setCameraLockY 조합만으로 "아래로 들어가는 지하 파이프", "오른쪽으로 나가는 출구", "위로 솟아오르며 등장하는 출구" 등 서로 다른 연출을 스크립트 하나로 전부 표현합니다. 연출 순서:

  1. 플레이어 조작을 StartWarp()으로 차단, 렌더 레이어를 배경 뒤로 보내 파이프 안으로 들어가는 것처럼 보이게 함.
  2. Vector3.Lerp로 1.5칸만큼 파이프 방향으로 서서히 이동.
  3. 블랙 오버레이 활성화(암전) → 목적지 좌표로 순간 이동 → 카메라를 ConfigureCamera()로 목적지에 맞게 재설정.
  4. 암전 해제 후 반대 방향으로 exitDistance만큼 다시 Lerp 이동(등장 연출).
  5. EndWarp()으로 조작권 반환.

FlagPole — 높이 비례 점수 + 숨은 1UP

float poleTopY = transform.position.y + 5.25f;
if (poleTopY - marioY <= 0.5f)
{
    // 꼭대기 정확히 잡음 → 1UP + 2000점
    GameManager.Instance.AddLife(...);
    GameManager.Instance.AddScore(2000);
}
else
{
    // 잡은 높이에 비례해 1000~2000점 사이 100점 단위로 보간
    float heightRatio = Mathf.InverseLerp(bottomPos.position.y, poleTopY, marioY);
    int score = Mathf.RoundToInt(Mathf.Lerp(1000f, 2000f, heightRatio) / 100f) * 100;
}

이후 MarioCtrl.ClearRoutine()이 (1) 마리오와 깃발을 각자의 속도로 동시에 하강 → (2) 깃대 오른쪽으로 위치 이동 및 방향 반전(Flip) → (3) 성 방향으로 점프 → (4) 착지 후 걷기 애니메이션으로 성문까지 자동 보행 → (5) 도착 시 GameManager.CalculateTimeScoreRoutine()을 호출해 남은 시간을 10점 단위로 환산하며 점수를 빠르게 올리는 연출을 실행합니다.

포인트: 이 시퀀스 동안에는 isClearing/isClearJumping 두 개의 플래그로 일반 입력 기반 물리(FixedUpdate)를 완전히 차단하고, 코루틴이 rigidbody2D.velocity를 직접 제어합니다. "평소의 자동 물리 로직"과 "컷씬성 강제 이동"이 동시에 같은 Rigidbody를 건드리면 충돌하므로, 플래그로 두 로직이 상호 배타적으로 동작하도록 명확히 구분한 것이 핵심 설계 포인트입니다.
12

면접 예상 질문 Q&A

면접관이 물어볼 법한 질문과, 코드 근거를 곁들인 답변 초안입니다. 클릭하면 펼쳐집니다.

Q. 왜 GameManager와 SoundManager를 싱글톤으로 만들었나요? MonoBehaviour 싱글톤의 단점은 없었나요?▾

답변 방향: 씬이 5회 이상 전환되는 구조(타이틀→전환→스테이지→전환→...)에서 점수/코인/목숨/오디오처럼 게임 전역에 걸쳐 하나만 존재해야 하는 상태를 유지하려면 씬 전환에도 살아남는 오브젝트가 필요했습니다. DontDestroyOnLoad + Instance == null 가드로 최초 1개만 살아남게 구현했습니다.

단점 인지: 싱글톤은 전역 상태이므로 테스트가 어렵고 의존관계가 암묵적이 되는 단점이 있습니다. 이 프로젝트 규모(1개 스테이지, 팀 없이 개인 개발)에서는 트레이드오프가 합리적이라 판단했지만, 규모가 커진다면 ScriptableObject 기반 데이터 컨테이너나 의존성 주입(DI) 프레임워크(Zenject 등)로 전환을 고려할 것입니다.

Q. IEnemy 인터페이스를 왜 만들었나요? 상속(base class)으로도 되지 않나요?▾

답변 방향: Goomba와 Koopa는 이동 방식, 상태 개수, 죽는 연출이 서로 완전히 다릅니다. 공통 로직을 강제로 추상 클래스에 넣으면 오히려 불필요한 결합이 생깁니다. 반면 "피격당했을 때 반응해야 한다"는 행위(contract)만 공유하면 되므로 인터페이스가 더 적합했습니다.

실제 이점: Fireball, InteractableBlock, 심지어 다른 Koopa 껍질까지 상대의 구체 타입을 몰라도 GetComponent<IEnemy>()?.HitByFireball() 한 줄로 통일된 처리가 가능해졌습니다. 새로운 적을 추가해도 호출부를 전혀 수정할 필요가 없습니다(OCP).

Q. 점프 물리를 Rigidbody2D의 기본 gravityScale이 아니라 직접 계산한 이유는?▾

답변 방향: SMB1 원작은 "점프 버튼을 얼마나 오래 누르는지"에 따라 점프 높이가 달라지고, 달리다 점프하면 더 멀리/오래 뜹니다. 이는 중력이 상황(상승/하강, 버튼 유지 여부, 점프 시작 속도)에 따라 실시간으로 바뀌어야 가능한데, gravityScale 하나로는 이런 동적 전환을 표현할 수 없습니다.

그래서 FixedUpdate에서 매 프레임 상황에 맞는 currentGravity 값을 계산해 vel.y -= currentGravity * Time.fixedDeltaTime으로 직접 속도를 갱신하고, 마지막에 rigidbody2D.velocity = vel로 한 번에 반영하는 방식을 택했습니다. Unity 물리엔진의 충돌/침투 처리 이점은 유지하면서, 이동/중력 계산의 디테일만 직접 제어하는 하이브리드 방식입니다.

Q. 별(Star) 무적 상태의 색상 반짝임을 왜 Animation이나 Shader가 아니라 텍스처 스와핑으로 구현했나요?▾

답변 방향: 처음엔 Color 틴트를 고려했지만, 원작 별 상태는 스프라이트 전체가 레드→블랙→그린으로 팔레트 자체가 바뀌는 것이라 단순 색상 곱(Multiply)으로는 원하는 느낌이 안 나왔습니다. 그래서 3장의 완성된 텍스처를 미리 만들어두고 MaterialPropertyBlock으로 _MainTex만 교체하는 방식을 택했습니다. MaterialPropertyBlock을 쓴 이유는 material 프로퍼티에 직접 접근하면 머티리얼 인스턴스가 매번 새로 생성되어 드로우콜 배칭이 깨지기 때문입니다.

트러블슈팅 경험: Update에서 텍스처를 바꾸면 그 후 Animator가 그림을 다시 덮어써서 반짝임이 안 보이는 문제가 있었고, 이를 LateUpdate로 옮겨 애니메이터 처리 이후 마지막에 강제로 덮어쓰는 방식으로 해결했습니다.

Q. 오브젝트 풀링(Object Pooling)은 적용하지 않았나요? 왜인가요?▾

솔직한 답변: 이번 프로젝트에는 적용하지 않았습니다. 파이어볼, 적 처치 이펙트, 점수 팝업처럼 빈번하게 생성/파괴되는 오브젝트들이 전부 Instantiate/Destroy를 직접 사용합니다. 스테이지 하나 규모(1-1)에서는 체감 성능 이슈가 없었지만, 여러 스테이지·더 많은 동시 발사체가 있는 확장판이라면 가장 먼저 개선할 지점으로 꼽고 있습니다 (Fireball, FloatingScore, BrickDebris가 우선 후보).

Q. MarioCtrl.cs가 굉장히 큽니다(1000줄 이상). 문제라고 생각하나요?▾

정직한 자기평가: 네, 이 프로젝트에서 가장 큰 구조적 약점으로 인지하고 있습니다. 이동, 점프, 상태 변신, 무적 연출, 워프, 깃발 클리어, 사운드 트리거까지 마리오와 관련된 거의 모든 로직이 한 클래스에 몰려 있어 God Object에 가깝습니다.

개선 방향(면접에서 제시할 답): 실제로 리팩터링한다면 (1) 이동/점프 물리를 MarioMovement, (2) 상태 변신을 MarioTransformState(또는 상태 패턴 클래스 계층), (3) 워프/깃발 연출을 MarioSequencePlayer 식으로 컴포넌트를 분리하고, MarioCtrl은 이들을 조합하는 퍼사드(Facade) 역할만 맡도록 바꿀 것입니다. 실제 산업 현장의 캐릭터 컨트롤러 구조(예: 상태 패턴 + 별도 이동 컴포넌트)를 참고해 설계를 다시 잡고 싶습니다.

Q. 충돌 처리에 OnCollisionEnter2D와 OnTriggerEnter2D를 각각 어떤 기준으로 나눠 썼나요?▾

답변 방향: 물리적으로 실제 부딪혀서 밀어내거나 반사되어야 하는 대상(굼바, 쿠파, 버섯, 별, 파이어볼)은 Collision2D(비트리거 콜라이더)로 처리해 Unity 물리엔진이 위치를 실제로 막아주도록 했고, 단순히 "지나가면 발동"하는 판정형 오브젝트(코인, 워프 파이프 진입 영역, 깃발 트리거, 구덩이 DeathZone, 블록 위 아이템/적 감지)는 Trigger로 처리했습니다. 몸이 있는 오브젝트인가, 통과 가능한 판정 영역인가를 기준으로 나눴습니다.

Q. PPU(Pixel Per Unit) 기반 상수 설계는 왜 그렇게 했나요?▾

답변 방향: SMB1의 실제 물리 수치(가속도, 최고속도, 점프속도 등)는 커뮤니티에서 "픽셀/프레임²" 또는 "픽셀/초" 단위로 역분석되어 공개되어 있습니다. 이 숫자를 Unity의 월드 단위(1 Unit)로 변환하려면 전부 PPU로 나눠야 하는데, 상수마다 그 계산을 반복하는 대신 C# 프로퍼티의 getter (private float MAX_WALK { get { return 93.75f / PPU; } })로 선언해 PPU 값 하나만 바꾸면 모든 이동 수치가 함께 스케일되도록 만들었습니다. 유지보수성과 원작 고증의 정확도를 동시에 잡기 위한 선택입니다.

Q. 테스트 코드는 없는데, 어떻게 이 로직들이 정상 동작하는지 검증했나요?▾

솔직한 답변: 유닛 테스트는 작성하지 않았습니다. 대신 OnDrawGizmos로 groundCheck, 블록 위 감지 박스 등 물리 판정 영역을 에디터에서 시각적으로 확인할 수 있게 했고, Debug.Assert로 필수 참조(애니메이터, 리지드바디 등) 누락을 Start() 시점에 바로 잡아내도록 했습니다. 또한 I 키로 남은 시간을 강제로 조정하는 개발자 치트를 넣어 100초 경고 연출처럼 자주 재현하기 번거로운 상황을 즉시 테스트할 수 있게 했습니다.

개선 방향: 순수 물리 계산 로직(가속/감속/중력 계산)은 MonoBehaviour와 분리해 Unity Test Framework의 Edit Mode 테스트로 검증 가능한 구조로 바꿀 수 있다고 생각합니다.

13

한계점 & 개선 방향 (자기 평가)

면접관이 가장 신뢰하는 답변은 "잘한 것"보다 "한계를 정확히 알고 있는 것"입니다. 스스로 정리한 약점과 개선안입니다.

1. MarioCtrl의 책임 과다 (God Object)

이동/점프/변신/무적/사망/워프/클리어 연출이 한 클래스에 집중. 상태 패턴 클래스 계층 또는 컴포넌트 조합(Movement / TransformState / SequencePlayer)으로 분리 예정.

2. 오브젝트 풀링 미적용

Fireball, FloatingScore, BrickDebris 등 빈번히 생성/파괴되는 오브젝트가 매번 Instantiate/Destroy를 호출. 스테이지가 늘어나면 GC 부담이 커질 수 있어 우선 개선 대상.

3. GameObject.Find류 호출의 잔존

GameObject.FindGameObjectWithTag("Player"), FindGameObjectsWithTag("FireBall") 등이 런타임에 반복 호출됨. 참조를 캐싱하거나 이벤트/매니저를 경유하는 방식으로 교체하면 더 안전하고 빠름.

4. 매직 넘버 다수 존재

0.2f, 0.3f, 0.7f 같은 충돌 판정 임계값이 여러 클래스에 흩어져 있음. ScriptableObject 기반 설정값으로 중앙화하면 밸런스 조정과 유지보수가 쉬워짐.

5. 유닛 테스트 부재

물리 계산 로직이 MonoBehaviour 안에 강결합되어 있어 Unity 없이 순수 로직만 테스트하기 어려움. 순수 C# 클래스로 물리 계산을 분리하면 Edit Mode 테스트 도입이 가능.

6. 싱글톤 남용 가능성

규모가 커질수록 GameManager.Instance 직접 참조가 늘어나 암묵적 의존성이 커짐. 이벤트 기반(옵저버) 통신이나 DI로 점진적 전환을 고려.

이 프로젝트를 통해 배운 것

  • Unity의 기본 물리(AddForce, gravityScale)만으로는 표현할 수 없는 세밀한 조작감은 매 프레임 velocity를 직접 계산해야 함을 체감.
  • 인터페이스로 "행위 계약"만 공유하면 서로 다른 구현체(Goomba/Koopa/Shell)가 호출부 변경 없이 확장 가능하다는 것을 실제로 체험.
  • 코루틴이 "시간에 따른 순차 연출"을 상태 플래그+Update보다 훨씬 읽기 쉽게 만든다는 것.
  • 싱글톤+DontDestroyOnLoad는 편리하지만 프로젝트가 커질수록 결합도 문제가 눈에 보이기 시작한다는 것(이번엔 규모상 감내 가능했음).

면접 전 최종 체크리스트

  • MarioCtrl의 FixedUpdate 흐름(가속→스퀴드→점프 중력→최종 velocity 적용)을 화면 없이 말로 설명할 수 있는가
  • IEnemy를 쓴 이유와, 상속 대신 인터페이스를 택한 이유를 30초 안에 설명할 수 있는가
  • 싱글톤 패턴의 장단점과, 이 프로젝트 규모에서 그 트레이드오프가 왜 합리적이었는지 설명할 수 있는가
  • 가변 점프(눌러서 높이 조절)를 중력 스위칭으로 구현한 원리를 그림 없이 말로 설명할 수 있는가
  • 이 프로젝트의 가장 큰 구조적 약점(MarioCtrl 비대화)과 개선안을 먼저 나서서 언급할 수 있는가
  • 오브젝트 풀링을 안 쓴 이유와, 언제 도입이 필요할지에 대한 본인 생각 정리
  • 씬 전환 흐름(Title → Transition → Stage → Transition)과 그 사이 GameManager가 하는 역할을 설명할 수 있는가
