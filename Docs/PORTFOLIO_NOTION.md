## 프로젝트 소개

> 1985년 패미컴 원작의 조작감을 "비슷하게"가 아니라 **원본 수치 그대로** 재현하는 것을 목표로 잡은 2D 플랫포머입니다.

원작 클론을 만들 때 가장 흔한 실패는 "보기에는 마리오인데 만져 보면 마리오가 아닌" 결과물입니다. 그래서 이 프로젝트는 스프라이트를 옮기는 작업이 아니라 **NES가 쓰던 이동·중력 상수를 유니티 단위계로 환산해 이식하는 작업**을 축으로 삼았습니다. 물리를 먼저 고정한 뒤, 그 위에 상태 변신 · 적 AI · 연출 시퀀스를 얹는 순서로 1인 개발했습니다.

### (플레이어 물리) NES 원본 상수를 이식한 가변 중력 점프

#### 개요

Rigidbody2D의 기본 중력과 `AddForce`로 점프를 만들면 "떠 있는 시간이 긴 마리오"가 나옵니다. 원작은 **점프를 시작하는 순간의 수평 속도에 따라 상승 속도와 중력이 통째로 바뀌고**, 점프 키를 누르고 있는 동안에는 더 가벼운 중력이 적용되는 구조인데, 이를 물리 머티리얼이나 중력 스케일 조정으로는 재현할 수 없었습니다. 이를 해결하기 위해 유니티의 중력을 끄고 원작 수치를 PPU(Pixel Per Unit) 단위로 환산해 속도를 직접 적분하는 방식으로 구현했습니다.

#### 설계

- 모든 상수를 `프레임 단위 픽셀 값 ÷ PPU(16)` 형태의 프로퍼티로 정의
  - 원작 수치를 그대로 남겨 두어 어떤 값을 왜 그렇게 잡았는지 나중에도 추적 가능하게 함
  - 스프라이트 임포트 설정이 바뀌어도 PPU 한 곳만 고치면 전체가 따라오게 함
- 점프 시작 시점의 `|velocity.x|`로 **정지 / 걷기 / 달리기** 3구간을 나눠 상승 속도와 중력 세트를 결정
  - 원작의 "달리면 더 멀리, 더 오래 난다"는 감각이 별도 분기 없이 자연스럽게 나옴
- 상승 중 점프 키 유지 여부에 따라 `가벼운 중력 / 무거운 중력`을 매 프레임 교체 (가변 점프)
- 감속을 `키를 뗀 마찰(DEC_REL)`과 `반대 방향 입력(DEC_SKID)`으로 분리
  - 미끄러지듯 도는 스키드 모션이 애니메이션이 아니라 물리 결과로 나오게 함

| 구간 | 상승 속도 | 키 뗀 중력 | 키 유지 중력 |
| --- | --- | --- | --- |
| 정지 (`vx` < 1) | 280 | 1575 | 450 |
| 걷기 (`vx` < 2.5) | 280 | 1800 | 421.875 |
| 달리기 | 300 | 2025 | 562.5 |

*(단위: 원작 픽셀 값. 실제 적용 시 전부 ÷16)*

#### 관련 코드 / 처리 흐름

```csharp
private float PPU = 16f;
private float MAX_RUN  { get { return 153.75f  / PPU; } }
private float DEC_SKID { get { return 365.625f / PPU; } }  // 방향 전환 시 마찰

// 점프 시작 순간의 수평 속도가 상승 속도와 중력 세트를 함께 결정한다
if (absVx < 1f)        { vel.y = JUMP_SPEED_IDLE; currentGravityBase = STOP_FALL; currentGravityHold = STOP_FALL_A; }
else if (absVx < 2.5f) { vel.y = JUMP_SPEED_IDLE; currentGravityBase = WALK_FALL; currentGravityHold = WALK_FALL_A; }
else                   { vel.y = JUMP_SPEED_RUN;  currentGravityBase = RUN_FALL;  currentGravityHold = RUN_FALL_A;  }

// 상승 중 + 키 유지일 때만 가벼운 중력 → 누른 시간만큼 더 높이 뜬다
currentGravity = (vel.y > 0 && isJumpButtonHeld) ? currentGravityHold : currentGravityBase;
vel.y = Mathf.Max(vel.y - currentGravity * Time.fixedDeltaTime, -MAX_FALL);
```

> 📸 **[다이어그램]** 수평 속도 3구간 → 상승 속도·중력 세트 결정 흐름도. 세 구간의 점프 궤적을 겹쳐 그린 그래프가 함께 있으면 가장 좋습니다

> 📸 **[스크린샷]** 인스펙터에서 `MAX_WALK` / `MAX_RUN` 값을 바꿔 가며 비교한 화면 (전/후 2장)

### (플레이어 상태) 상태 전환 시 콜라이더·판정 박스·애니메이터 일괄 동기화

#### 개요

마리오는 Small(16×16)과 Super/Fire(16×32)의 몸 크기가 다르고, 숙이면 다시 반으로 접힙니다. 크기 변경을 스프라이트만 바꿔서 처리하면 **콜라이더는 큰 채로 남아 지나갈 수 있는 틈을 못 지나가거나, 바닥·머리 판정 위치가 어긋나 블록을 못 치는 문제**가 생겼습니다. 이를 해결하기 위해 상태 변경을 단일 진입점으로 모으고, 콜라이더·바닥 체커·머리 체커·애니메이터 교체를 한 번에 처리하도록 구성했습니다.

#### 설계

- 상태 전환은 `ChangeMarioState(string)` 하나만 호출하면 되도록 창구를 단일화
  - 상태가 늘어나도 호출부(아이템 획득 · 피격 · 워프)를 고치지 않아도 됨
- 크기 관련 처리를 `SetColliderSize()`와 `SetCheckers()` 두 함수로 분리 (SRP)
  - 숙이기처럼 "상태는 그대로인데 크기만 바뀌는" 경우에 그대로 재사용
- `AnimatorOverrideController`로 Small/Super를 같은 상태 머신 위에서 스프라이트만 교체
  - 상태 머신을 복제하지 않아 전이 조건을 한 곳에서만 관리
- 콜라이더의 `edgeRadius`만큼 크기를 미리 빼서 지정
  - 둥근 모서리가 바깥으로 튀어나와 실제 판정이 커지던 문제를 크기 계산 단계에서 흡수
- 바닥 판정은 콜라이더 접촉이 아니라 `Physics2D.OverlapBox`로 별도 수행
  - 상태별로 발밑 박스의 위치·너비를 따로 줄 수 있어 판정이 스프라이트를 따라감

> 📸 **[스크린샷]** Scene 뷰에서 `OnDrawGizmos`로 그린 바닥/머리 판정 박스 — Small · Super · 숙이기 3장 비교

### (연출) MaterialPropertyBlock 텍스처 스와핑 기반 스타 무적 팔레트 점멸

#### 개요

원작의 스타 무적은 색을 어둡게 덧칠하는 연출이 아니라, **NES 팔레트 자체가 프레임 단위로 교체되는** 연출입니다. `SpriteRenderer.color`로 틴트를 주면 원작과 전혀 다른 색이 나오고, 스프라이트를 통째로 갈아 끼우면 재생 중인 애니메이션이 끊깁니다. 이를 해결하기 위해 색이 다른 스프라이트 시트를 미리 준비해 두고, 애니메이터가 재생하는 스프라이트는 그대로 둔 채 렌더러가 참조하는 **텍스처만** 교체하는 방식으로 구현했습니다.

#### 설계

- 팔레트 교체는 `MaterialPropertyBlock`의 `_MainTex` 지정으로 처리
  - 머티리얼 인스턴스가 새로 생기지 않아 배칭이 깨지지 않음
  - 원복은 `SetPropertyBlock(null)` 한 줄이면 되어 되돌리는 경로가 단순해짐
- 교체 주기는 코루틴이 "무엇을 칠할지"만 지시하고, 실제 적용은 `LateUpdate`에서 수행
  - 애니메이터가 스프라이트를 갱신한 **뒤에** 덮어쓰게 되어 한 프레임 깜빡임이 사라짐 (아래 트러블슈팅 참고)
- 시간 계산은 `WaitForSecondsRealtime` 기준
  - 변신 연출이 `Time.timeScale = 0`으로 게임을 멈추는 구간이 있어, 무적 시간이 그만큼 늘어나지 않게 함
- 파이어 마리오는 상·하체 렌더러가 분리되어 있어 상체용/하체용 텍스처 배열을 따로 둠

```csharp
// 코루틴은 "무엇을 칠할지"만 지시한다
currentStarTexture = starPaletteTextures[paletteIndex % starPaletteTextures.Length];

// 실제 적용은 애니메이터 갱신 이후인 LateUpdate에서
private void LateUpdate()
{
    if (isStarInvincible)
        ApplyStarTexture(currentStarTexture, currentUpperStarTexture, currentLowerStarTexture);
}
```

### (상호작용) 블록 피격 시 OverlapBoxAll 레이더로 위쪽 오브젝트에 연쇄 반응

#### 개요

원작에서는 블록을 아래에서 치면 그 위에 서 있던 적이 뒤집혀 죽고, 굴러가던 버섯은 튀어 오르며 방향을 바꿉니다. 이 반응을 물리 충돌로 처리하려 하면 블록이 실제로 움직이는 것이 아니라 **애니메이션으로만 들썩이기 때문에 충돌 자체가 발생하지 않는 문제**가 있었습니다. 이를 해결하기 위해 피격 순간 블록 바로 위 영역을 박스로 훑어 대상에게 직접 반응 함수를 호출하는 방식으로 구현했습니다.

#### 설계

- 타격 순간 블록 위 `0.9 × 0.2` 영역에 `Physics2D.OverlapBoxAll`을 1회 발사
  - 상시 감지가 아니라 이벤트 시점 1회 검사라 비용이 프레임에 남지 않음
- 감지 대상은 태그가 아니라 **컴포넌트 유무**로 분기
  - `IEnemy`면 `HitFromBelow()`, `MushroomAI`/`StarAI`면 `BounceAndChangeDirection()`
  - 새 아이템을 추가할 때 태그 체계를 건드리지 않고 컴포넌트만 붙이면 됨
- 반응 내용을 대상 스스로 정의하게 만들어, 블록은 "무엇을 맞혔는지"만 알고 "어떻게 죽는지"는 모르게 분리
- `OnDrawGizmos`로 검사 박스를 에디터에 상시 표시
  - 레벨 배치 중 판정 범위를 눈으로 확인할 수 있어 위치 조정이 빨라짐

> 📸 **[스크린샷]** Scene 뷰의 마젠타색 검사 박스 기즈모 + 블록을 쳐서 굼바가 뒤집히는 순간의 게임 화면

### (적 AI) IEnemy 인터페이스로 사망 경로를 통일하고 Koopa를 3상태 FSM으로 구성

#### 개요

적은 밟히기 · 블록에 받히기 · 파이어볼 피격 · 등껍질에 치이기 등 여러 경로로 죽는데, 이를 호출하는 쪽(마리오 · 블록 · 파이어볼 · 다른 등껍질)이 전부 다릅니다. 호출부마다 `GetComponent<Goomba>()`, `GetComponent<Koopa>()`를 나열하면 **적이 추가될 때마다 관련 없는 스크립트를 전부 수정해야 하는 문제**가 있었습니다. 이를 해결하기 위해 피격 경로를 인터페이스 3개 메서드로 규정하고, 호출부는 구체 타입을 모르게 만들었습니다.

#### 설계

- `IEnemy`를 `Squished()` / `HitFromBelow()` / `HitByFireball()` 세 가지 **원인**으로 정의 (DIP)
  - 결과(죽는다)가 아니라 원인을 인터페이스로 잡아, 같은 원인에 다르게 반응하는 적을 자연스럽게 표현
  - 실제로 굼바는 `Squished()`에 찌그러지고, 엉금엉금은 같은 호출에 등껍질로 변합니다
- 엉금엉금은 `Walking / ShellIdle / ShellMoving` 3상태 FSM으로 구성하고 상태 전환 시 콜라이더 크기까지 함께 교체
- 날아가는 등껍질이 다른 적과 충돌하면 상대에게 `HitByFireball()`을 호출한 뒤 **즉시 return**
  - 아래쪽 벽 판정 로직을 타지 않아 원작처럼 여러 마리를 관통하며 연쇄 처치가 성립
- 벽 판정은 `contact.normal.x`의 절댓값으로 하되 Player·Enemy 태그를 제외
  - 마리오나 다른 적을 벽으로 오인해 방향이 뒤집히던 동작을 막음

> 📸 **[다이어그램]** Koopa 3상태 FSM (전이 조건: 밟힘 / 옆에서 접촉 / 벽 충돌) + IEnemy를 호출하는 4개 주체를 화살표로 표시

### (씬·전역) 싱글톤 매니저와 전환 씬 라우팅으로 게임 흐름 제어

#### 개요

점수 · 코인 · 목숨 · 남은 시간은 씬을 넘어 유지되어야 하고, BGM은 씬 전환에 끊기면 안 됩니다. 또 사망 · 타임업 · 게임오버는 각각 다른 화면을 보여 준 뒤 서로 다른 곳으로 이어져야 해서, **각 씬이 다음 씬을 직접 부르면 흐름이 여러 스크립트에 흩어지는 문제**가 있었습니다. 이를 해결하기 위해 데이터와 사운드를 `DontDestroyOnLoad` 싱글톤으로 분리하고, 화면 전환은 전용 씬 하나가 상태 값을 보고 분기하도록 구성했습니다.

#### 설계

- `GameManager`(데이터·흐름)와 `SoundManager`(오디오)를 책임 단위로 분리 (SRP)
  - 사운드가 필요 없는 씬에서도 데이터는 유지되고, 반대도 성립
- 전환 화면을 씬 3개로 나누지 않고 `TransitionType` enum 하나로 분기하는 단일 씬으로 통합
  - 목숨 소모 후 어디로 갈지(재시작 / 게임오버) 판단을 `LoseLife()` 한 곳에 모음
  - 타임업도 결국 목숨을 깎는 처리이므로 같은 경로로 흘려보내 분기 중복을 없앰
- 100초 경고는 코루틴에서 **BGM 정지 → 경고음 재생 → 클립 길이만큼 대기 → 빠른 BGM 재생** 순으로 직렬화
  - 경고음과 BGM이 겹쳐 들리던 문제를 `warningSound.length` 만큼 대기해 해결
- 최고 점수는 클리어 정산이 끝나는 시점에만 `PlayerPrefs`에 기록
  - 매 득점마다 디스크에 쓰지 않도록 저장 시점을 한 곳으로 제한

> 📸 **[다이어그램]** 씬 흐름도 — Title → Transition(Intro) → Stage → (Death / TimeUp / Clear) → Transition → … 분기

### (카메라·디스플레이) 256×240 강제 레터박스와 원작식 단방향 카메라

#### 개요

원작은 256×240 해상도를 전제로 만들어져, 와이드 모니터에서 화면비를 늘리면 픽셀이 뭉개지고 원래 보여선 안 될 영역까지 보입니다. 또 SMB1의 카메라는 **오른쪽으로만 이동하고 절대 되돌아오지 않으며**, 지상에서는 Y축이 완전히 고정되어 있어 일반적인 추적 카메라로는 재현되지 않았습니다. 이를 해결하기 위해 뷰포트를 계산해 레터박스를 만들고, 카메라 추적 규칙 자체를 원작 규칙으로 다시 작성했습니다.

#### 설계

- 실행 시 현재 화면비와 목표 비율(256/240)을 비교해 `Camera.rect`를 조정
  - 세로가 길면 위아래, 가로가 길면 좌우에 블랙바를 만들어 어떤 해상도에서도 비율이 깨지지 않음
- X 추적에 `Mathf.Max(현재 X, 목표 X)`를 적용해 **되돌아오지 않는 카메라**를 구현
  - 별도 상태나 플래그 없이 한 줄로 원작의 단방향 스크롤 규칙을 만족
- Y축은 `lockY` 플래그로 고정값 사용 / 자유 추적을 전환
  - 지상은 Y 고정, 지하는 완전 고정(`isStatic`)으로 구역 성격에 맞게 설정
- 카메라 모드 전환 권한을 `ConfigureCamera()` 하나로 열어 두고 워프 파이프가 이를 호출
  - 지하 진입·지상 복귀처럼 카메라 규칙이 바뀌는 지점을 레벨 배치만으로 지정 가능

```csharp
// SMB1 규칙: 카메라는 오른쪽으로만 간다
targetX = Mathf.Max(transform.position.x, targetX);
transform.position = new Vector3(targetX, lockY ? fixedY : targetY, transform.position.z);
```

> 📸 **[스크린샷]** 16:9 모니터에서 좌우 블랙바가 적용된 실행 화면 (레터박스 적용 전/후 2장)

### (최적화) 카메라 거리 기반 적 수면·기상 및 오브젝트 디스폰

#### 개요

레벨의 모든 적이 시작과 동시에 움직이면, 플레이어가 도착하기도 전에 굼바가 낭떠러지에 빠져 사라집니다. 원작도 같은 이유로 **화면에 가까워질 때 적을 활성화**하는데, 이 동작이 없으면 레벨 디자인이 의도대로 재현되지 않았습니다. 이를 해결하기 위해 적을 물리 비활성 상태로 배치해 두고 카메라와의 거리로 깨우도록 구현했습니다.

#### 설계

- 스폰 시 `rb.simulated = false`로 물리 자체를 꺼 두고, 카메라와의 X 거리가 임계값 안으로 들어오면 활성화
  - `SetActive` 대신 물리만 끄는 방식이라 깨어날 때 컴포넌트 재초기화 비용이 없음
- 카메라가 충분히 지나친 적은 `Destroy`로 회수
  - 카메라가 되돌아오지 않는 규칙 덕분에 "다시 필요해질 일이 없다"가 보장되어 안전하게 파괴 가능
- 파이어볼도 같은 기준(카메라 X 거리 · 낙하 Y 하한)으로 디스폰
  - 화면 밖에서 살아남아 원작의 "화면당 2개" 제한을 잠식하던 동작을 막음

> 📸 **[스크린샷]** Hierarchy에서 아직 잠들어 있는 적과 깨어난 적이 구분되게 보이는 화면 (Rigidbody2D `simulated` 체크 상태 포함)

### (Trouble Shooting) 스타 무적 팔레트가 매 프레임 원래 색으로 되돌아감

#### 문제 상황

스타를 먹으면 마리오가 빠르게 색을 바꿔야 하는데, 실제로는 원래 색이 계속 비쳐 보이며 점멸이 지저분하게 보였습니다. 코드상 텍스처 교체는 분명히 실행되고 있어서 처음에는 교체 주기나 텍스처 파일이 잘못된 것으로 의심했습니다.

#### 문제와 해결

**[ 애니메이터가 렌더러를 뒤늦게 덮어쓰는 문제 ]**

- **문제**: 코루틴에서 텍스처를 바꿔도 화면에 반영되지 않거나 한 프레임만 나타났다 사라짐
- **원인**: 스프라이트 애니메이터의 갱신이 코루틴/`Update`보다 나중에 실행되어, 지정한 텍스처를 애니메이터가 그대로 덮어씀
- **해결 과정**:
  1. 텍스처 파일과 교체 주기를 먼저 의심했으나, 로그상 교체는 정상 실행되고 있음을 확인
  2. 실행 순서 문제로 방향을 돌려 적용 시점을 `Update` → `LateUpdate`로 이동
  3. 코루틴은 "어떤 텍스처를 칠할지" 지시만 하고, 실제 적용은 `LateUpdate`가 매 프레임 수행하도록 역할을 분리
  4. 원복은 개별 텍스처 복원이 아니라 `SetPropertyBlock(null)`로 지정 자체를 걷어내는 방식으로 정리
- **결과**: 애니메이션이 어떤 프레임을 재생하든 팔레트가 유지되어, 점멸이 원작과 같은 속도로 안정적으로 표시됨
- **한계**: 현재 `LateUpdate`에서 `MaterialPropertyBlock`을 매 프레임 새로 생성하고 있어 무적 지속 시간(10초) 동안 불필요한 할당이 발생합니다. 필드로 캐싱하면 제거되는 비용이지만, 무적 구간이 짧고 프로파일러에서 체감할 만한 스파이크가 관측되지 않아 후순위 개선 항목으로 남겨 두었습니다

### (Trouble Shooting) 무적 상태에서 적에게 닿아도 적이 죽지 않음

#### 문제 상황

스타를 먹은 뒤 적에게 그대로 돌진하면, 마리오가 데미지를 입지 않는 것까지는 맞는데 **적도 죽지 않고 그냥 통과**해 버렸습니다. 무적 처리를 넣기 전에는 정상적으로 처리되던 부분이라 무적 로직 자체를 의심했습니다.

#### 문제와 해결

**[ 충돌을 없앤 결과 충돌 이벤트도 사라진 문제 ]**

- **문제**: 무적 중 적과 접촉해도 아무 반응이 없음
- **원인**: 마리오가 적에게 밀려나는 것을 막으려고 `Physics2D.IgnoreLayerCollision`으로 Player↔Enemy 충돌을 껐는데, 적을 죽이는 처리도 같은 `OnCollisionEnter2D`에 있어 함께 사라짐
- **해결 과정**:
  1. 무적 중에만 충돌이 안 잡히는 것을 확인하고, 원인이 무적 로직이 아니라 레이어 충돌 무시임을 특정
  2. 충돌을 다시 켜는 대신, **"밀려남"과 "적 처치"는 애초에 다른 관심사**라고 판단하고 분리하기로 결정
  3. 물리 충돌은 끈 상태를 유지하고, 적 처치 판정만 `FixedUpdate`에서 `OverlapBoxAll`로 별도 수행
  4. 감지 박스 높이를 Small(1.0) / Super·Fire(2.0)로 상태에 맞춰 바꾸고, 여러 마리가 동시에 닿을 수 있으므로 `All` 계열을 사용
- **결과**: 무적 중 밀려남 없이 이동하면서 접촉한 적을 모두 처치하는 원작 동작이 재현됨
- **한계**: 감지 박스 크기가 코드에 상수로 들어가 있어 실제 스프라이트 크기와 완전히 일치하지는 않습니다. 콜라이더 크기에서 값을 가져오는 편이 정확하지만, 판정이 조금 넉넉한 쪽이 무적 상태의 손맛에 오히려 맞아 현재 값을 유지했습니다

### (Trouble Shooting) 파이어 마리오의 렌더 상태가 세 벌로 갈라짐

#### 문제 상황

파이어 마리오는 달리면서 파이어볼을 던져야 해서 상체와 하체 애니메이터를 분리했습니다. 그러자 **워프 중 파이프 뒤로 들어가는 처리, 클리어 시 좌우 반전, 스타 팔레트 교체가 파이어 상태에서만 동작하지 않는** 현상이 각기 다른 시점에 나타났습니다.

#### 문제와 해결

**[ 렌더러가 1개에서 3개로 늘어나며 생긴 누락 ]**

- **문제**: 워프 시 파이어 마리오만 파이프 앞에 그려지고, 깃대 클리어 시 상·하체가 반전되지 않음
- **원인**: 기존 코드가 몸통 `SpriteRenderer` 하나만 조작하도록 작성되어 있었는데, 파이어 상태에서는 조작 대상이 몸통·상체·하체 3개로 늘어나 있었음
- **해결 과정**:
  1. 상태별로 실제 활성화되는 렌더러가 무엇인지 정리 (Small·Super = 몸통 1개 / Fire = 상·하체 2개)
  2. Sorting Layer 변경을 `ChangeSortingLayer(layerName, order)` 한 함수로 묶어 3개 렌더러를 항상 함께 처리
  3. 워프 진입 시 원래 레이어와 order를 저장해 두고 종료 시 복원하도록 하여, 어느 상태로 워프해도 같은 경로를 타게 함
  4. 애니메이터 파라미터 전달도 `UpdateAnimations()` 한 곳으로 모아 상·하체에 동일 파라미터를 함께 넘김
- **결과**: 워프 · 클리어 · 스타 무적 모두 상태와 무관하게 동일하게 동작하며, 이후 연출을 추가할 때도 함수 하나만 호출하면 되도록 정리됨
- **한계**: 3개 렌더러를 배열이나 리스트로 일반화하지 않고 개별 필드로 다루고 있어, 파트가 더 늘어나면 각 함수를 다시 수정해야 합니다. 현재 파트 수가 고정이고 더 늘릴 계획이 없어 지금 구조를 유지했습니다

### (Trouble Shooting) 깃대 클리어 연출 중 마리오가 튀거나 미끄러짐

#### 문제 상황

깃대를 잡으면 마리오가 일정한 속도로 미끄러져 내려와 성으로 걸어가야 하는데, 하강 도중 위아래로 튀거나 착지 후 목표 지점을 지나쳐 계속 걸어가는 현상이 있었습니다.

#### 문제와 해결

**[ 연출용 이동과 수동 물리 계산이 동시에 실행되는 문제 ]**

- **문제**: 코루틴이 `transform.position`을 직접 옮기는 동안 `FixedUpdate`의 속도 계산이 같은 프레임에 함께 적용됨
- **원인**: 이 프로젝트는 중력을 직접 적분하는 구조라, 연출 중에도 `FixedUpdate`가 계속 중력과 입력을 반영하고 있었음
- **해결 과정**:
  1. `isClearing` 플래그를 추가해 연출 중 `FixedUpdate`를 조기 반환시킴
  2. 그러나 깃대에서 뛰어내리는 구간은 **물리가 필요한 연출**이라, 전부 막으면 착지 판정을 쓸 수 없음을 확인
  3. `isClearJumping` 플래그를 하나 더 두어 "물리는 돌리되 입력은 무시"하는 중간 상태를 정의
  4. 해당 구간에서는 입력값(`h`, 점프·대시 버튼)을 강제로 0/false로 대체해 물리 계산만 살림
  5. 성으로 걷는 구간은 `WaitForFixedUpdate`로 물리 타이밍에 맞춰 속도를 직접 지정
- **결과**: 하강 → 반전 → 점프 → 착지 → 걷기까지 한 코루틴 안에서 끊김 없이 진행되며, 목표 X 좌표에서 정확히 멈춤
- **한계**: 연출 중 제어권을 상태 머신이 아니라 bool 플래그 2개로 표현하고 있어, 연출이 더 늘어나면 플래그 조합을 매번 확인해야 합니다. 현재 이런 연출이 클리어 시퀀스 하나뿐이라 플래그 방식이 읽기에 더 명확해 유지했습니다. 이 구조를 정리하는 과정에서 `FixedUpdate`의 중력 계산 자체에 결함이 있는 것을 발견했고, 아래 트러블슈팅에서 수정했습니다

### (Trouble Shooting) 재점검에서 발견해 수정한 상태 제어 결함 2건

#### 문제 상황

두 결함 모두 플레이 중에는 잘 드러나지 않는 종류였습니다. 하나는 "점프가 원작보다 아주 조금 낮다" 정도로만 느껴졌고, 다른 하나는 특정 순서로 아이템을 먹었을 때만 재현되어 버그로 인지되지 못했습니다. 기능이 모두 동작하는 상태에서 `MarioCtrl`을 처음부터 다시 읽으며 두 건을 찾아 수정했습니다.

#### 문제와 해결

**[ 점프 첫 프레임에 중력이 두 번 차감되던 문제 ]**

- **문제**: 원작 상수를 그대로 이식했는데도 점프 최고 높이가 원작보다 미세하게 낮게 나옴
- **원인**: `FixedUpdate` 안에 중력 차감이 두 곳에 있었는데, 점프 처리 블록이 `grounded = false`로 바꾼 직후 아래의 공중 중력 블록이 **같은 프레임에 이어서** 실행되어 점프를 시작하는 프레임에만 중력이 두 번 적용됨
- **해결 과정**:
  1. 상수 환산식(÷PPU)과 `Time.fixedDeltaTime` 곱을 먼저 검산했으나 값 자체는 정확함을 확인
  2. 중력이 실제로 몇 번 적용되는지 프레임 단위로 추적해, 점프 첫 프레임에만 두 번 차감되는 것을 특정
  3. 점프 처리 블록의 역할을 **"상승 속도와 중력 세트를 결정하는 것"까지로 한정**하고, 차감은 하지 않도록 변경
  4. 중력 차감을 공중 중력 블록 한 곳으로 통일해, 어떤 경로로 진입하든 프레임당 정확히 한 번만 적용되도록 정리
- **결과**: 점프 시작 프레임에 여분으로 빠지던 `28.125 × 0.02 ≈ 0.56 unit/s`가 사라졌습니다. 정지 점프의 초기 상승 속도(`280 ÷ 16 = 17.5 unit/s`) 대비 약 3%에 해당하는 손실이었습니다 *(코드 상수로부터의 계산값)*
- **한계**: 수정 전 수치를 기준으로 배치한 블록 높이·발판 간격이 1-1에 남아 있어, 도달 가능 여부를 구간별로 다시 검증해야 합니다. 값 자체의 결함만 제거한 단계이며 레벨 재검증은 아직 끝나지 않았습니다

**[ 별 획득 시 무관한 코루틴까지 함께 중단되던 문제 ]**

- **문제**: 피격 무적으로 깜빡이는 중에 별을 먹으면 마리오가 **투명한 채로 고정되거나 무적이 풀리지 않는** 상태가 됨
- **원인**: 별을 겹쳐 먹었을 때 지속 시간을 리셋하려고 `StopAllCoroutines()`를 호출했는데, 이 호출이 같은 컴포넌트의 피격 무적 깜빡임 · 변신 연출 · 클리어 시퀀스까지 전부 중단시킴. 깜빡임 코루틴은 렌더러를 껐다 켜는 도중에 죽으면 마지막 상태(꺼짐)로 굳고, `isInvincible = true`도 되돌려지지 않음
- **해결 과정**:
  1. 재현 조건을 좁혀, 별 단독 획득이 아니라 **다른 코루틴이 돌고 있을 때만** 발생함을 확인
  2. 원인을 `StopAllCoroutines()`의 적용 범위로 특정
  3. 별 코루틴을 `Coroutine` 참조로 보관하고, 중복 획득 시 그 참조 하나만 `StopCoroutine`으로 정지
  4. 코루틴이 정상 종료하거나 조기 반환할 때 참조를 `null`로 비워, 끝난 코루틴을 다시 정지시키지 않도록 정리
- **결과**: 피격 무적·변신 연출 중에 별을 먹어도 각 연출이 끝까지 재생되며, 마리오가 투명하거나 무적으로 굳는 상태가 사라짐
- **한계**: 상태 전이 규칙 자체는 여전히 bool 플래그 4개(`isInvincible` · `isStarInvincible` · `isWarping` · `isClearing`)의 조합으로 표현되어 있어, 상태가 늘어나면 같은 종류의 충돌이 다시 생길 수 있습니다. 플레이어 상태를 단일 FSM으로 정리하는 것이 근본 해결책이지만, 현재 조합 수에서는 플래그 쪽이 읽기 쉬워 유지했습니다

```csharp
// 수정 전: 같은 컴포넌트의 모든 코루틴이 함께 죽는다
// StopAllCoroutines();
// StartCoroutine(StarTextureSwapRoutine());

// 수정 후: 별 코루틴만 참조로 들고 있다가 그것만 정지시킨다
if (starRoutine != null) StopCoroutine(starRoutine);
starRoutine = StartCoroutine(StarTextureSwapRoutine());
```

### (Trouble Shooting) 스타 무적 중 파이어볼을 던지면 상체 스프라이트가 깨짐

#### 문제 상황

파이어 마리오 상태로 스타를 먹고 공격 키를 누르면, 던지는 동안 **상체만 알아볼 수 없는 픽셀 덩어리로 깨져** 보였습니다. 하체는 멀쩡했고 스타가 끝나면 원래대로 돌아왔습니다. 스타 무적은 색만 바꾸는 기능인데 왜 모양이 무너지는지 처음에는 연결되지 않았고, 팔레트 이미지가 잘못 만들어진 것으로 의심했습니다.

#### 문제와 해결

**[ 발사 모션만 다른 스프라이트 시트를 참조하고 있던 문제 ]**

- **문제**: 스타 상태에서 파이어볼을 던지는 0.15초 동안 상체 스프라이트가 깨짐
- **원인 분석**: 스타 무적은 `LateUpdate`에서 `_MainTex`를 팔레트 텍스처로 통째로 갈아끼우는 방식입니다. 그런데 스프라이트의 UV(`textureRect`)는 **자기 원본 시트의 크기를 기준으로 정규화**되어 있어, 교체 텍스처가 원본과 크기·배치가 같을 때만 성립합니다. 상체 애니메이션 중 발사 모션(`Upper_Shoot`)만 `throwfireball.png`(34×32)를 참조하고 나머지(Idle · Run · Jump · Skid)는 `fire_upper.png`(96×24)를 참조하는데, 스타 상체 팔레트는 후자의 리컬러 3장뿐이었습니다. 크기가 다른 시트가 씌워지면서 UV가 엉뚱한 영역을 샘플링한 것이 깨짐의 정체였습니다
- **해결 과정**:
  1. "하체는 멀쩡하고 상체만, 그것도 던지는 동안에만" 깨진다는 점에서 원인을 특정 애니메이션 클립으로 좁힘
  2. `.anim` 파일이 참조하는 텍스처 GUID를 `.png.meta`의 GUID와 대조해, 상체 클립 5개 중 `Upper_Shoot`만 다른 시트를 쓰고 있음을 확인
  3. 두 시트의 해상도가 다른 것을 확인하고, 원인을 팔레트 이미지 결함이 아니라 **UV 기준 불일치**로 특정
  4. 스타 무적 중에는 파이어볼 발사 입력을 막음. 원작에서도 스타 연출이 우선이고, 달리기는 `FixedUpdate`에서 같은 버튼을 별도로 읽으므로 조작감에는 영향이 없음을 확인
  5. 재발 방지로, 팔레트를 칠하기 전에 **현재 스프라이트의 원본 시트 크기가 팔레트와 일치하는지 검사**하고 다르면 덮어쓰기를 건너뛰도록 안전장치를 추가
- **결과**: 스타 상태에서 어떤 조작을 해도 상체가 깨지지 않으며, 앞으로 다른 시트를 쓰는 모션이 추가되어도 그 프레임만 원본 그림으로 표시되고 나머지는 정상적으로 점멸합니다
- **한계**: 같은 시트인지를 **가로·세로 크기 비교로만** 판정하고 있어, 해상도가 우연히 같지만 프레임 배치가 다른 시트가 추가되면 걸러내지 못합니다. 원본 텍스처 참조를 직접 들고 비교하는 편이 정확하지만, 현재 상·하체가 쓰는 시트가 고정되어 있어 비용이 낮은 크기 비교로 두었습니다

**[ 발사 직후 별을 먹으면 깨짐이 스타 지속 시간 내내 유지되던 문제 ]**

- **문제**: 파이어볼을 던진 직후(0.15초 이내)에 별을 먹으면, 같은 깨짐이 순간이 아니라 **무적 10초 내내** 지속됨
- **원인**: 발사 모션은 `isShooting`을 켜고 0.15초 뒤 다시 끄는 코루틴으로 제어됩니다. 당시 별 획득 처리가 `StopAllCoroutines()`를 호출하고 있어서, 이 코루틴이 **대기 중에 죽으며 끄는 줄에 도달하지 못했습니다.** `isShooting`이 `true`로 고정되어 상체 애니메이터가 `Upper_Shoot` 상태에 갇힌 것입니다
- **해결 과정**:
  1. 증상이 "순간형"과 "지속형" 두 가지로 나뉜다는 것을 확인하고 재현 조건을 분리
  2. 지속형은 입력 차단만으로는 막히지 않음을 확인 — 별을 먹기 **전에** 이미 발사했기 때문
  3. 앞선 `StopAllCoroutines()` 결함 수정(별 코루틴만 정지)으로 코루틴이 더 이상 중간에 죽지 않게 됨
  4. 그럼에도 파라미터가 켜진 채 별에 진입하는 순간이 남아 있어, 별 코루틴 시작 시 `isShooting`을 명시적으로 내려 이중으로 차단
- **결과**: 두 경로 모두에서 재현되지 않으며, 앞의 코루틴 결함이 이 버그의 **지속형 변종을 만들고 있었다**는 연결 관계도 함께 정리됨
- **한계**: 애니메이터 bool 파라미터의 수명을 코루틴에 의존해 관리하는 구조 자체는 그대로입니다. 상체 모션이 더 늘어나면 "파라미터가 켜진 채 남는" 같은 종류의 문제가 재발할 수 있으며, 모션 종료를 코루틴이 아니라 애니메이션 이벤트나 상태 종료 시점에 맡기는 것이 근본 해결책입니다. 현재는 모션이 하나뿐이라 구조를 유지했습니다

```csharp
// 스프라이트 UV는 자기 원본 시트 크기 기준이라, 크기가 다른 텍스처를 씌우면 깨진다.
// 크기가 맞는 프레임에만 팔레트를 칠하고, 아니면 원본 그림을 그대로 보여준다.
void SwapMainTex(SpriteRenderer sr, Texture2D starTex)
{
    if (sr == null) return;

    Sprite cur = sr.sprite;
    bool sameAtlas = starTex != null && cur != null && cur.texture != null
                     && cur.texture.width == starTex.width
                     && cur.texture.height == starTex.height;

    if (!sameAtlas)
    {
        sr.SetPropertyBlock(null); // 덮어쓰기 해제 → 애니메이터의 원본 그림이 그대로 나옴
        return;
    }

    MaterialPropertyBlock mpb = new MaterialPropertyBlock();
    sr.GetPropertyBlock(mpb);
    mpb.SetTexture("_MainTex", starTex);
    sr.SetPropertyBlock(mpb);
}
```

- 잡은 높이를 `InverseLerp`로 0~1 비율로 환산해 1000~2000점을 100점 단위로 지급

- 클리어 후 남은 시간을 1초당 10점으로 환산하며 카운트다운, 정산 종료 후 성 깃발 게양 애니메이션 → 최고 점수 저장 순으로 직렬화

**벽돌 파괴 파편 (`InteractableBlock.BreakBlock`)**
- 4방향 파편에 서로 다른 초기 속도와 회전 토크를 주입해 원작의 흩어지는 궤적을 재현

**블록 타입 통합 (`BlockType` enum)**
- 물음표 / 벽돌 / 히든 / 코인 벽돌을 스크립트 1개로 처리하고, 마리오 상태(`isSuper`)에 따라 나오는 아이템(버섯↔꽃)과 파괴 가능 여부를 분기

**코인 100개 1UP**
- 코인 획득을 `AddCoin()` 한 곳으로 모아 100개 도달 시 목숨 증가와 팝업 생성을 함께 처리

**획득 점수 팝업 (`FloatingScore`)**
- 점수 추가 함수를 위치 인자 유무로 오버로딩해, 호출부에서 팝업 필요 여부만 선택하면 되도록 구성
